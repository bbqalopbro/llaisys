# B300 W4A8：按 K32 顺序累加的独立实验

本文记录 2026-09-12 的真实激活调错与独立 CUDA 实验。测试对象是 DeepSeek V4 Flash 的 FP8 E4M3 激活 × FP4 E2M1 权重 GEMM；激活按 K128、权重按 K32 使用 UE8M0 scale，输出 BF16，累加使用 FP32。这里只改变 small-M GEMM 的归约顺序，未修改模型默认后端。

## 为什么单算子通过后仍需整模型验证

原始冻结实现 [w4a8_decode_sm103.cu](../src/ops/deepseek_v4/nvidia/w4a8_decode_sm103.cu) 让 warp 中各 lane 累加自己负责的 K32 分组，最后进行树形 shuffle 归约。随机激活与真实权重的单算子测试误差很小，但完整 chat 测试仍出现显著 logits 偏差。

为排除 harness 或模型代码变化，先用当前代码、同一原始 chat golden、相同配置重跑全 TileLang 控制：8 个 case 的 352 个 teacher-forced step 全部 logits bitwise exact。原始 tree CUDA 实验的对应 352 步只有 343 步 argmax 相同，最大 relative L2 为 0.2933683，最小 cosine 为 0.9562315。该实验不能作为整模型数值验收通过的证据。控制报告的总 `all_passed` 还混入旧功能答案门槛，判断数值控制应读取逐 case 的 `numerical_gate_passed` 和 `all_logits_exact`。

随后只跑原始 chat case 0 的两步，沿真实模型路径逐次比较 small-M CUDA 与注册好的 TileLang。两者接收完全相同的 A、SA、B、SB；固定返回 TileLang 结果给模型，避免前面出现的 CUDA 差异污染后续激活。该诊断共执行 6,777 次 FP4 GEMM，其中 6,501 次 small-M 双实现对照、276 次大 M TileLang 调用。

原始 tree 版本的 6,501 次对照中，34 次调用出现非 exact 输出，共 36 个 BF16 元素不同。首次差异来自 `layers.1.ffn.experts.8.w2.weight`，M=2、N=4096、K=2048，最大绝对误差 0.0078125；最坏 relative L2 为 0.0002112199，来自 `layers.3.ffn.experts.153.w1.weight`。报告保存了首次及最坏调用的权重/scale SHA256、A/SA/SB dtype、shape、stride 和数值范围。

这组证据说明：当前数据中少量 BF16 舍入差异足以对应明显的完整模型数值偏离。具体经过哪些量化边界、路由选择或后续累加放大，尚未逐层归因，不能把推测写成已验证的因果链。

## ordered-K32 改动

官方 `inference/kernel.py::fp4_gemm_kernel` 的外层循环按 K32 分组顺序更新 FP32 累加器。新实验保留 warp 并行加载及每个 K32 分组的 dot/scaling，然后通过 `__shfl_sync` 按 group 0、1、2……的顺序把结果交给 lane 0，用 `__fadd_rn` 串行累加，最后执行 BF16 round-to-nearest 转换。原来的最终树形归约被移除。

每个 K32 分组内部仍使用原实现的 FP4/FP8 解码、packed-half 乘法和 FP32 dot 累加；scale 仍保持原 K32 边界。新实验没有改量化格式、改变激活数值或重新量化权重。

这是针对 B300 SM103 的 warp/SIMT CUDA 实现，不能称为新 Tensor Core GEMM。它通过向量化 packed weight 访问、warp 协作及 M 特化复用已量化数据；ordered 归约增加了串行依赖，性能必须重新测量。官方 TileLang 内部 dot32 的 Tensor Core 归约并未被逐指令复刻，因此不能仅凭算法说明宣称所有输入 bitwise 等价。

| variant | ordered 实验中的实际行为 |
| --- | --- |
| 0、1 | 4 个输出 warp；按 K32 group 升序累加 |
| 2 | 8 个输出 warp；按 K32 group 升序累加 |
| 3 | 保留原来的 4 warp split-K/tree 归约；没有做 ordered 修正 |

本文的真实激活 ordered 对照使用 variant 1。不能把它的结果推广到 variant 3。

## 源码、ABI 与构建身份

原始冻结源码未改。实验最初写入 `build/experiments/w4a8_ordered_k32/w4a8_decode_sm103_ordered_k32.cu`，随后以相同字节复制到可提交的 [w4a8_decode_sm103_ordered_k32.cu](../src/ops/deepseek_v4/nvidia/w4a8_decode_sm103_ordered_k32.cu)。仅 `decode<M,Warps>` 的归约部分不同，旧头文件 [w4a8_decode_sm103.h](../src/ops/deepseek_v4/nvidia/w4a8_decode_sm103.h) 及 C ABI 保持一致。

| 对象 | SHA256 |
| --- | --- |
| 原始冻结 tree 源码 | `24236330188c6bd85a79fe264b995a63dcab921e9a340047c2abe6ca1e4d456e` |
| ordered 实验/发布源码 | `817027b2ce5bec32ba4b4d6d4d25658b106cc786d5ee8de97c44d90cf96ced33` |
| 共用头文件 | `9a7beec1cc5697bdd13f210555aff4345b2de3f261f7930396f98a84d89d5688` |
| 本次实际测试的 ordered `.so` | `cb7a8759ae5c36855f977abb4ce7756a98d2c389ccc047dfd1f12c01251a8fa2` |

实际编译命令、编译器版本、24 个特化的 ptxas 资源记录、CPU ABI 检查和源码关系见 [ordered 构建 manifest](../benchmark_results/deepseek_v4_cuda/w4a8_ordered_k32_build_20260912.json)。24 个特化均为零 stack、零 spill，host 参数拒绝检查通过；这些结果本身不构成 GPU 正确性或性能证明。

两个库仍返回同一 ABI version 字符串 `llaisys-w4a8-sm103-experimental-v2`。该字符串只能表示 ABI，不能区分 tree 与 ordered 的数值实现。必须根据 manifest 的源码 SHA、`library_sha256` 与运行报告中实际加载库的 SHA 建立对应关系。

冻结 GPU harness 记录旧 base `.cu` 和选定 `.so` 的 hash，不会自动发现新实验 `.cu`。解释 ordered 结果时必须同时读取上述 build manifest 的 `published_source`、`experimental_sha256` 和 `library_sha256`；单看 harness 中的旧 `.cu` hash 会错误归属源码。

可从发布源码单独构建一个新库：

```bash
mkdir -p build/standalone_cuda
/usr/local/cuda/bin/nvcc -O3 -std=c++17 -arch=sm_103a \
  -DLLAISYS_B300_STANDALONE --shared -Xcompiler=-fPIC \
  --ptxas-options=-v \
  src/ops/deepseek_v4/nvidia/w4a8_decode_sm103_ordered_k32.cu \
  -o build/standalone_cuda/libw4a8_ordered_k32_sm103.so
```

此命令只编译 ordered `.cu`，由同目录提供旧 `.h`。不得把 tree 和 ordered 两个 `.cu` 在启用 guard 时链接进同一个库，因为它们导出相同 C ABI 符号。常规工程未定义 `LLAISYS_B300_STANDALONE` 时，这两个实验翻译单元都不启用。重新构建的库应重新记录 SHA；本文列出的库 hash 绑定 manifest 内的实际原构建命令。

## 已完成的 ordered 真实激活验证

使用 [diagnose_w4a8_model.py](../tools/deepseek_v4_cuda/diagnose_w4a8_model.py)，传入 `--variant 1 --library build/experiments/w4a8_ordered_k32/libw4a8_ordered_k32_sm103.so`，完成原始 chat case 0 两步的 shadow 对照。

- 6,501/6,501 次 small-M 调用与注册 TileLang 输出 bitwise exact，非 exact 调用数和不同元素数均为 0。
- 实际覆盖 M=1…8，以及 (N,K)=(2048,4096)、(4096,2048) 两种真实专家投影形状。
- 模型固定收到 TileLang 结果，case 0 的两步 logits 与原始 golden bitwise exact；该结果证明本次真实激活算子对照，不等同于 ordered 后端替换后的完整模型验收。
- 当前 checkpoint 的完整 168,430,204,680 字节重新计算 SHA256，结果为 `024836b412ccd5c539bb130842842247d9c427f99c3a1e21ed35ea08ddcc0aa2`，与原始 published chat report 的 payload 身份一致。
- 报告中 `source_unchanged=true`、`checkpoint_unchanged=true`，并完成 CUDA 同步。

报告：[ordered 真实激活 shadow](../benchmark_results/deepseek_v4_b300_w4a8_ordered_shadow_20260912.json)，SHA256 为 `65dac3e0ff59485aa402198f9ce328543c9f7bc890f660642b82bece1878ff6c`。

原始对照见 [tree 真实激活 shadow](../benchmark_results/deepseek_v4_b300_w4a8_activation_shadow_20260912.json)、[当前代码 TileLang 控制](../benchmark_results/deepseek_v4_b300_w4a8_model_tilelang_control_20260912.json) 和 [tree 完整模型失败报告](../benchmark_results/deepseek_v4_b300_w4a8_model_chat_20260912.json)。保留这些失败和控制证据用于重现调错过程。

## 完整模型与自由生成验收

使用 [probe_w4a8_model.py](../tools/deepseek_v4_cuda/probe_w4a8_model.py) 完成完整原始 chat 套件，命令如下；需在已配置 Torch/TileLang/Hadamard 的 B300 运行环境中执行：

```bash
python tools/deepseek_v4_cuda/probe_w4a8_model.py \
  --suite chat --variant 1 --free-generation \
  --library build/experiments/w4a8_ordered_k32/libw4a8_ordered_k32_sm103.so \
  --output benchmark_results/deepseek_v4_b300_w4a8_ordered_model_chat_20260912.json
```

以上为本次实际命令；从发布源码按前述命令重新构建时，`--library` 应改为新库路径，并记录新库的构建身份。

[ordered 完整模型报告](../benchmark_results/deepseek_v4_b300_w4a8_ordered_model_chat_20260912.json) 返回 `status=passed`、`all_passed=true`。报告 SHA256 为 `c31b83f792d7ca6e8ecc7ea170f42da44cf7f18c5e953c313b9e2f7164389664`。

- 8 个 chat case，prompt 长度分别为 19、41、48、28、32、62、2011、21；352 个 teacher-forced step 全部 logits bitwise exact，relative L2 全部为 0，argmax 全部一致。
- 8 个 case 的独立自由生成 IDs 全部与原始 golden 相同，共生成 352 个 token；没有将 golden token 回灌给自由生成路径。
- 真实 MP1 权重只加载一次；完整 43 层各执行 704 次，对应 teacher-forced 和自由生成两轮。
- 实际调用 ordered CUDA small-M 660,930 次、大 M TileLang 38,220 次。M=1…8 固定 variant 1，M>8 是预先声明的形状分派，错误不会触发换后端；FP8 和其他算子保持 TileLang/Torch 基线。
- 原始 checkpoint payload、原始 golden 文件 hash 和源模型 hash 均通过验证；源码、checkpoint、全局默认 dtype 未变，最终 CUDA 同步完成，未导入官方 `inference/model.py` 执行模型。

功能答案命中为 5/8，与原始 published baseline 完全一致。原始套件已有 3 个功能未命中，不能作为此次 GEMM 数值退化；数值验收与答案功能命中在报告中分开记录。上述通过结论只覆盖本次 variant 1 和明确列出的模型套件，不构成全输入 bitwise 等价证明。

## ordered variant 1 性能与边界测试

[边界报告](../benchmark_results/deepseek_v4_b300_w4a8_ordered_edge_20260912.json) 的 128 个 case 全部通过，包含边界形状、guard 完整性、CUDA Graph 输入修改和并发 stream 检查。[真实权重微基准](../benchmark_results/deepseek_v4_b300_w4a8_ordered_decode_20260912.json) 的 32 个形状全部通过；variant 1 对 TileLang 的输出全部 exact，热缓存 Graph 单次 GEMM 中位延迟范围为 7.848–32.459 μs，相对本次同跑 TileLang 为 2.887–17.691 倍。

加速比为对照时间除以 ordered 时间，小于 1 表示 ordered 较慢。因此，本次 M=8 的 ordered variant 1 比 DeepGEMM adapter 慢，不能宣称全面超过 DeepGEMM。variant 3 的数值算法仍是 tree，即使微基准显示更快，也不能用来替代 variant 1 的完整模型通过结论。

这里仅使用同一次运行中的后端对照。本次 TileLang 绝对耗时与未修改算法的 variant 3 也与旧运行不同，不能把跨运行时间差全部解释为 ordered 归约代价。GPU 频率等状态原因没有实测，本记录不对原因作断言。

热缓存测量为同一操作数在 CUDA Graph 中重复 32 次；冷缓存测量先读写 530,579,456 字节缓冲区扰动约 132,644,864 字节 L2，再测单次操作。容量覆盖不保证逐条缓存行被硬件失效。计时排除权重 I/O、激活量化、JIT、Graph 构造和缓存扰动本身；DeepGEMM adapter 时间包含 SA/SB 转 FP32 与内部 scale 处理，没有复用预转换 scale。逻辑 footprint/时间不是硬件测得的 DRAM 带宽。

三份报告均为 `all_passed=true`、`source_unchanged=true`，并绑定同一 ordered `.so` SHA；边界/微基准/冷暖报告的 SHA256 分别为 `0643a152e2cdf9c925a0dba068fdbe56e022f7afc4c091aedcd622e3bd2d3d1b`、`a1fb5b1538a6b3d6c4dfb9b9be0cb7d02ce82a960e4a05b6e5b7b000afb4724d`、`f0db3fccdeb7cf77e5820f1fd632e53af1e6f4cb3cd8c37466390bc272d9b4d6`。

这些是算子级测量。完整模型正确性 runner 的单步耗时包含 Python 调度、其他算子及状态处理，没有做受控服务性能实验，因此不据此宣称端到端 TTFT、TPOT 或吞吐提升。
