# B300 FP8 prefill CUDA 后端与实测（2026-09-12）

已实现独立 CUDA C ABI 后端，保持 DeepSeek-V4-Flash-0731 的 E4M3 权重/激活和
UE8M0 尺度，用 cuBLASLt MXFP8 Tensor Core 执行投影。Slurm **26587** 完成第 2 层
五类真实权重 × 三种 M 的 **15 组测试**，全部通过数值、graph 与参数边界检查。

这是合成激活上的单算子结果；没有把该后端接入默认 43 层模型或宣称端到端加速。

## 实现选择及 B300 特性

接口计算 `C[M,N] = A[M,K] @ B[N,K]^T`，输出 BF16，累积采用 FP32。
A scale 为 M×(K/128)，B scale 为 (N/128)×(K/128)，均为 UE8M0；A/B 的连续
FP8 E4M3 payload 保持原样。

CUDA 13 文档中的 `VEC128_32F` 和 `BLK128x128_32F` 只支持 Hopper CC 9.0，不能
直接用作 B300 后端。CC 10.3 采用 `VEC32_UE8M0`：CUDA kernel 将一个 K128
scale 精确复制为四个 K32 scale；B scale 同时沿其覆盖的 128 行展开，写入 cuBLASLt
要求的 tiled layout。每 128 行 × 4 个 scale 占 512 字节，使用合并的 32 位写入。
这是元数据重排，没有权重反量化、重新量化或额外 scale 舍入。
[NVIDIA CUDA 13 scaling 文档](https://docs.nvidia.com/cuda/archive/13.0.3/cublas/index.html#narrow-precision-data-types-usage)

预展开 B scale 的存储约占 FP8 B payload 的 3.125%，与把整份 B 展开为 BF16/FP32
不同。A scale 每次更新，B scale 在权重尺度不变时只准备一次。数学上等价的尺度
展开仍可能改变 Tensor Core 的部分和归约顺序，所以没有要求逐位相同，也没有省略
与原始 TileLang 和 FP32 参考的比较。

代码由两部分构成：项目编写的 CUDA scale kernel、shape/layout/stream/生命周期
适配；NVIDIA cuBLASLt 提供的 Tensor Core GEMM。它是可供 C++ runtime 直接调用
的原生 CUDA 后端，执行库不依赖 Python/Torch/ATen/TileLang；它**不是项目自研的
Tensor Core GEMM 主内核**。后者若要成立，还需自行实现/维护主循环、流水线、
片上存储与 MMA 调度，并做独立验证。

## 已测试性能

硬件为 NVIDIA B300 SXM6 AC，CC 10.3；CUDA 13.0、Torch 2.13.0+cu130，运行时
`cublasLtGetVersion()` 返回 **130101**。对照使用实际模型随附的 TileLang kernel，
TileLang 0.1.8/TVM-FFI 0.1.8.post2。原生 DSO 链接 `libcublasLt.so.13`，CUDA runtime
由 nvcc 默认静态链接；Torch 仅属于 harness。

时间单位为 μs。原生列包含 A scale 重排、GEMM，以及 M 不对齐时的输入 padding/
输出 copy；两条路径均预先分配输出。

每个正式样本：graph 含 20 个重复调用，重放 20 次，以 CUDA events 计时；共五个
样本并取中位数。warmup、JIT、plan 创建、候选算法选择、B scale 一次性准备和
FP32 正确性计算均在计时之外。每个 shape 最多比较前四个 cuBLASLt heuristic，
随后固定选择；query_b 的 M=256/2105 选到 index 1，其余为 index 0。

A scale 单独耗时约 1.439–2.720 μs；这部分没有从 inclusive 时间中扣除。M=2105
内部补到 2112，多出的七行与输出截取代价均计入。原始样本、单独 GEMM 时间、
各候选时间与源码身份保留在 JSON。

这些是相同输入/权重反复执行的 graph 测量，没有逐次主动驱逐 L2，不能称为
冷缓存权重带宽或实际 serving 吞吐。也未覆盖多请求混合负载、设备争用、CPU API
提交间隔或全模型算子组合；不能把 6.661× 写成整模型加速。

## 数值与边界验收

从转换后的 MP1 checkpoint 读取 `layers.2.attn` 下的 `wq_a`、`wq_b`、`wkv`、
`wo_b`、`indexer.wq_b` 及其 `.scale`。加载器只读取所选 payload，严格核对
F8_E4M3/F8_E8M0、shape、长度与数据范围，记录 payload/full-header SHA256 与
文件前后身份。A 来自固定随机种子的合成 E4M3 激活，A scale 随机选择 UE8M0
指数；因此它还不是实际模型隐状态上的测试。

独立参考为 A/B 转 FP32 后按原始 scale 反量化，再执行关闭 TF32 的 FP32 GEMM。
这份 FP32 展开仅用于验证，不进入候选的初始化缓存或执行路径。

| 比较 | 15 组 relative L2 范围 | 最大绝对误差范围 |
|---|---:|---:|
| 原生 BF16 输出 vs TileLang BF16 输出 | 0.001798%–0.011285% | 0.015625–0.25 |
| 原生 BF16 输出 vs 独立 FP32 结果 | 0.165374%–0.167994% | 0.057587–0.495270 |
| TileLang BF16 输出 vs 独立 FP32 结果 | 0.165374%–0.167994% | 0.057587–0.495270 |

三项比较都检查有限值和预设 1% relative L2 门槛，15 组全部通过。这些输出并非
逐字节一致；不能根据非常接近的 FP32 误差范围声称两个算法完全相同。

其余实际通过的检查：

- native 与 TileLang 各自在 capture 后将输出填 NaN，graph 重放必须重新写出预期值，
  避免 warmup 留下的正确输出掩盖空 graph。
- 不换地址，把 A scale 翻倍后重放原生 graph，并执行 TileLang，对照 FP32 结果×2；
  15 组全部通过，验证捕获的 kernel 读取最新 scale 内容。
- A/B/C 使用 16B offset 的视图，输出与普通分配逐字节一致；cuBLASLt preference
  的四个矩阵最小对齐明确设为 16B，避免默认 256B 假设与 C ABI 合同不一致。
- 拒绝部分重叠输出和未对齐输出；每组两项，共 30 次拒绝检查。
- 每个投影的权重/scale 在不同 M 下身份一致，最终源码、DSO 和参考文件摘要未变。

## 执行设计和隔离

plan 固定设备、stream 和 shape，持有 descriptor、候选算法、scale/padding buffer
与 workspace；正式执行不分配显存、不修改 descriptor、不做设备同步。不同 stream
使用不同 plan，caller 负责 tensor 与 graph 生命周期，执行路径明确禁止重叠。
scale 展开使用 64 位 grid-stride 索引，避免大 shape 的循环计数溢出。

create/select/destroy 属于 capture 外的初始化/销毁操作。destroy 首先校验设备和
capture 状态；stream 同步失败后仍消费 plan 并尝试释放全部资源，返回独立状态码
2，不能把错误后的指针重复销毁。致命 CUDA context 错误不保证释放一定成功。

本文件位于现有 xmake CUDA glob 范围，故整个实现用
`LLAISYS_B300_STANDALONE` 编译宏保护，包括 CUDA 13 专有头文件。未开启宏时默认
构建得到空单元；已验证不带宏的 sm_80 编译和显式开启宏的 sm_103 独立库编译。
没有给默认 runtime 增加 cuBLASLt 链接依赖或自动选用新后端。
