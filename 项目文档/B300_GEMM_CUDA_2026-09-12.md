## W4A8：实现方式与实际合同

本实现使用 B300 支持的原生 packed FP8/FP4 转换及 `half2` 乘法，在 FP32 中完成
归约和缩放。它属于针对小 M 的 **SIMT CUDA kernel**，没有使用 Tensor Core MMA、
TMA 或 `tcgen05`。编译目标为 `sm_103a`；不能仅因编译到该架构就把它称为 Tensor
Core GEMM。另一个 FP8 prefill 实验的实现和结论见索引中的独立记录。

`C[M,N] = A[M,K] × B[N,K]^T` 的输入合同如下。

| 数据 | 格式与布局 |
| --- | --- |
| A | E4M3 FP8，`[M,K]`，连续列，可带非重叠行 padding |
| SA | UE8M0，`[M,K/128]`；每行每 128 个 K 元素一组 |
| B | E2M1 FP4，物理 `[N,K/2]`；每字节低 nibble 在前，连续存储 |
| SB | UE8M0，`[N,K/32]`；每行每 32 个 K 元素一组，连续存储 |
| C | BF16，连续 `[M,N]`，不得与输入内存重叠 |

显式支持 `1 <= M <= 8`、`1 <= N <= 65536`、`128 <= K <= 32768` 且 `K % 128 == 0`。
A/B 起始地址和 A 行 stride 按 16 字节对齐；C 按 2 字节对齐。SA/SB 的 UE8M0 字节
0 表示 `2^-127`，字节 255 按 NaN 解码，没有把零编码错误解释成零 scale。

CUDA 内核按 K32 组加载 16 字节 FP4 权重与 32 字节 FP8 activation，将对应两元素
转换为 `half2` 后相乘，同一权重组供 M 行复用。有限 E4M3×E2M1 的乘积幅度范围和
有效位数允许这些未缩放乘积精确表示为 FP16；CPU 穷举的 4064 组有限组合全部通过。
这项证明仅针对两数乘积，归约仍为 FP32，不能推导整个 GEMM 与另一归约树逐 bit
相同。K32 局部点积先乘对应 SA，再乘 SB，保留 FP32 舍入边界，最终转换 BF16。

| variant | 网格与归约方式 | 适用结论 |
| --- | --- | --- |
| 0 / 1 | 每 CTA 四个 warp，每 warp 一个输出列，warp 内分担 K32 组 | 0 当前是 1 的别名，没有自动选择最优实现 |
| 2 | 每 CTA 八个 warp，每 warp 一个输出列 | 较大的 CTA 不是所有形状都更快 |
| 3 | 每输出列一个 CTA，四个 warp 分担 K，借助 `partial[M][4]` 共享内存完成 CTA 内归约 | w1 的部分 M 形状有收益，w2 的部分形状更慢；没有全局 workspace 或 atomic |

C ABI 只发起异步 kernel，不分配、不同步、不重新量化 activation。Python 绑定动态
加载独立 `.so`，使用调用方当前 stream，并对输入/输出执行 `record_stream`；调用者
可提供独立输出，也可由绑定创建输出。参数非法、输出别名、地址范围溢出和非 10.3
设备显式失败，不静默切回其他后端。

## 数值与生命周期验收

真实权重来自既有 MP1 checkpoint，包含第 0 层 expert 0 的 w1/w2，以及第 3 层
expert 7 的 w1/w3。每个权重测试 M=1 至 8，共 **32 个真实权重形状、每形状 3 个
CUDA variant，96 次主对照全部通过**。JSON 保留各权重及 scale payload SHA256，
读取后先核对 FP4/E8M0 dtype、packed shape 和 K32 scale 形状，没有靠重解释错误
dtype 来制造有效输入。

activation 是固定种子 12092026 生成的 BF16 随机值，经官方
`act_quant(..., block_size=128, scale_fmt="ue8m0", scale_dtype=float8_e8m0fnu)`
量化。所有后端消费同一份 A/SA/B/SB。参考值用独立 FP4 码表和 UE8M0 解码，再以
关闭 TF32 的 FP32 矩阵乘得到 BF16 输出；同时对照官方 TileLang FP4 GEMM。门槛为
输出有限、relative L2 ≤ 0.005、cosine ≥ 0.99999；普通调用和 graph replay 均核验
数值。此处“真实”指权重 payload，不代表使用了整模型中间 activation。

最终 32 个形状中，30 个在三个 CUDA variant 下均与 TileLang 逐值一致；另两个
形状存在小量非零误差，不能把首轮 16 形状的 exact 结论推广成最终全部 exact：

| 权重 / M | 每个 variant 的不同元素数 | 最大绝对误差 | relative L2 |
| --- | ---: | ---: | ---: |
| `layers.0.ffn.experts.0.w1` / 6 | 1 | 0.015625 | 0.000089111978 |
| `layers.3.ffn.experts.7.w1` / 7 | 1 | 0.000003814697 | 0.000000020672 |

边界测试另有 **128 组**：M=1..8，`(N,K)` 为 `(1,128)`、`(3,256)`、`(13,4096)`、
`(129,128)`，variant=0/1/2/3。全部输出相对独立参考的 relative L2 为 0，输出前后
guard 值保持完整，覆盖所有 FP4 nibble 编码和 SB 的 UE8M0 字节 0。variant 3 还
通过 graph 捕获后修改 A 再 replay 的检查，避免只读到捕获前输出。

两个并发 stream 的额外测试在发起 variant 1/2 后释放外部输入引用，并施加 allocator
压力，再同步核对输出，验证 `record_stream` 的生命周期处理。32 个真实形状另外
检查了 variant 0/1/2/3 的非默认 stream、A/SA 行 padding 和同时存活的独立输出。
这些检查不等同于任意异步错误恢复、全部 CUDA API 错误或多 GPU 验收。

## 五后端对照与缓存测量范围

最终 memory 对照包含第 0 层 expert 0 的 w1/w2、M=1/4/8，共 **6 个形状 × 5 个
后端**，全部通过独立参考、TileLang、warm graph 与 cold graph 的数值检查。该矩阵
中的对照均逐值一致；它比前面的 32 形状矩阵范围小，不能覆盖 M6/M7 的误差记录。

DeepGEMM 使用已有 2.6.1，源码提交
`559d79fb6994a58b8a15b4b93bf13ccc16edf247`，以
`fp8_fp4_gemm_nt((A,SA.float()),(B.view(int8),SB.float()),out,recipe_a=(1,128),recipe_b=(1,32))`
调用。SA/SB 的 FP32 转换以及 DeepGEMM 内部需要的 scale layout kernel 都在每次
被计时的 operation 内；没有额外量化 A，也没有把转换后的 scale 在测量外预缓存。
因此下表比较的是实际 adapter GPU 工作量，不是独立 DeepGEMM 核函数的理论极限。

warm 路径每个 graph 连续执行同形状 GEMM 32 次，预热后测 9 个样本，按每次 GEMM
摊销 CUDA event 时间。每组 packed 权重约 4 MiB，重复同一权重会受益于 L2；不能
把 warm 时间解释为完整 MoE 权重轮转时的 DRAM 性能。

冷缓存实验通过驱动 API 查询 L2 为 132,644,864 字节（126.5 MiB），使用独立
530,579,456 字节（506 MiB，4×L2）缓冲区执行读写覆盖。单个 graph 按顺序执行
`eviction.add_(1) → external start event → 一次完整 operation → external end event`。
每次 replay 都重新覆盖，9 个样本；eviction 在事件跨度之外，graph 内事件节点避免
Python 提交间隙进入中间计时。这里只能称为容量覆盖式冷 L2 实验，不保证硬件已将
每条旧 cache line 全部失效。

下表均为微秒，中位数；V1/V2/V3 对应上文三个显式 CUDA variant。

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| w1 / 2048 / 4096 | 1 | 3.518 | 3.441 | 3.325 | 91.462 | 16.465 |
| w1 / 2048 / 4096 | 4 | 6.903 | 6.974 | 6.328 | 91.632 | 16.651 |
| w1 / 2048 / 4096 | 8 | 12.158 | 11.749 | 10.767 | 91.701 | 16.866 |
| w2 / 4096 / 2048 | 1 | 3.155 | 3.254 | 3.635 | 46.533 | 13.295 |
| w2 / 4096 / 2048 | 4 | 6.220 | 6.956 | 7.047 | 46.606 | 13.195 |
| w2 / 4096 / 2048 | 8 | 10.864 | 11.893 | 11.981 | 46.623 | 13.394 |

| 权重 | M | V1 cold | V2 cold | V3 cold | TileLang cold | DeepGEMM adapter cold |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| w1 | 1 | 10.240 | 10.240 | 8.192 | 104.448 | 24.576 |
| w1 | 4 | 12.288 | 12.288 | 12.288 | 104.480 | 24.576 |

很多 cold 中位数落在 8.192、10.240、12.288 等相隔 2.048 微秒的档位，但原始样本
还有更小步进，例如 10.080、10.432 微秒；不能据此断定硬件事件时钟分辨率固定为
2.048 微秒。受有限事件计时分辨率和波动影响，12.256 与 12.288 之类接近值不作为
稳定胜负证据。报告保留全部原始样本、最小/最大值，未只保存单次最优结果。

本次矩阵说明这些 SIMT 专用实现比所测 TileLang reference 路径快，并在所测小 M
范围内低于包含 scale 转换的 DeepGEMM adapter 时间。它不能推出 SIMT 在大 M、
其他权重布局或去除 adapter 成本后优于 Tensor Core。V3 在 w1 上的收益也没有扩展
到所有 w2 形状，因此没有更改默认选择策略。单独记录的 eager warm wall time 中，
CUDA 绑定约 19–20 微秒，而 graph 内核约 3–12 微秒，调用开销不可忽略。

JSON 中的 footprint 带宽只用逻辑输入/输出字节数除以时间，不是硬件计数器测得的
DRAM 带宽；也不包含多层模型、调度、路由、权重切换或请求 TTFT/TPOT。

## 本轮调错与版本演进

1. **量化合同纠错。** 初版 benchmark 只传 E8M0 `scale_dtype`，未传
   `scale_fmt="ue8m0"`。官方 kernel 由后者决定是否先对 scale 取二次幂，漏传会让
   A 用未取整 scale 量化、再存 E8M0 scale。即使两个后端同输入通过，也不能代表
   实际模型合同。正式 GPU 验证前已补齐参数并写入报告。
2. **graph 验收纠错。** 最初仅检查捕获输出有限，改为 warm/cold replay 都与独立
   参考核验，并加入修改输入后 replay 的用例；所有后端真实 shape 结果也保留。
3. **节点路径纠错。** 登录节点 `/tmp` 的独立 `.so` 不能假定在计算节点可见。
   正式使用共享仓库 `build/standalone_cuda/` 下的库；MP1 checkpoint 的 `/tmp`
   路径则是计算节点已有产物。复现前应在 allocation 内核实这两类路径。
4. **v1 到 v2。** 首轮 Slurm 26568 的 16 个真实形状测试 variant 1/2，通过且逐值
   一致。后续根据 M4/M8 的延迟表现增加 CTA 内 split-K variant 3，并扩到完整
   M1..8。Slurm 26584 的 32 形状揭示 M6/M7 小量非零误差，保持原门槛通过，没有
   为获取 exact 结论删掉这些形状。最终加构建宏后又用 Slurm 26586 重跑全部矩阵。
5. **审查补强。** 手工逐 Pair 检查确认 A 的 `(2p,2p+1)` 对应 B 的第 p 个 packed
   byte；本机 CUDA 头文件确认低 nibble 对应 `half2.x`。ABI 另修复超大 stride 的
   上界，保证 GPU int64 地址运算不溢出；输出别名在 launch 前拒绝。
6. **工具故障。** 早期 `.so` 的 `cuobjdump --dump-sass` 在登录节点触发工具自身
   SIGSEGV；`--dump-ptx`、resource usage 和 `nm` 可读。PTX 确认原生
   `cvt.rn.f16x2.e4m3x2`、`cvt.rn.f16x2.e2m1x2`、`mul.f16x2` 和 FP32 归约，
   没有 `mma`/`tcgen05`。该次反汇编器崩溃不是 CUDA kernel 运行失败，也不充当
   SASS 级优化证明；最终资源证据采用成功的 ptxas 构建日志。

## 完整模型替换探针：未通过数值门槛

## 尚未验收的范围

当前验证证明已列实际权重切片及形状的算子合同、限定数值门槛和独立组件性能。
本文初版 tree 的完整模型探针数值失败，不能升级为默认模型后端；后续 ordered

包含专家切换和实际调度的端到端性能。真实权重切片测试的 SHA256 不等于完整
checkpoint 扫描；本轮只有后续整模型探针做了上述完整身份验证。
